## What is now known that was not before

1. **Dynamic speculative decoding works with `dflash` on 0.31.0**, and a second `--speculative-config` in
   `EXTRA_ARGS` overrides the launcher's. No launcher change was needed, and no product file was changed.
   But the schedule from the experiment list can never engage on the shipped single-user profile: the pool
   holds at most 5 resident requests at K=7, so a bucket starting at batch 9 is unreachable. With the knee at
   4 (`[[1,3,7],[4,512,3]]`) the N=4 steady state improves +8.0% (ms/pass 56-57 → 43 ms) with C1 unchanged.
2. **The landscape's 1.7x TRITON/int8-vs-FlashInfer/fp8 gap (G3) is real but already collected on this card.**
   The shipped `CTX=fast` (FLASH_ATTN+bf16) is level with TRITON+int8 (+1.8%, i.e. noise), and both are ~1.4x
   faster than FlashInfer+fp8 (78.2 tok/s). FlashInfer loses its decode CUDA graphs with spec decode
   (`compilation.py:1462` warning, PIECEWISE only) — that downgrade is the whole gap.
3. **The drafter is not worse; the protocol is harder.** Greedy, thinking off: gsm8k 5.80, code 4.78, chat
   3.50 tokens per step. Our published ~3.3 is the low end of the drafter's range, and the GSM8K number sits
   at the published DFlash2 level (5.46, different sampling, not a like comparison).
4. **`reasoning_effort` is accepted by the served template** (low/xhigh; omitted = xhigh), thinking only.
   `low` raises acceptance: code +21.9%, chat +14.8% (free-run), gsm8k +5.2%.
5. **Thinking itself is the expensive mode**: xhigh vs thinking-off costs 15.7-23.3% tokens per step on the
   same prompts (E4 against E3).
6. **Graph capture size 64 → 40**: capture set narrows (0.13 → 0.12 GiB), +3.3-4.1% C1 (lead, not confirmed
   A-B-A), but the KV pool cannot grow — `KV_MEM` pins it in bytes.
7. **Machine-level facts** (in `2026-10-13-preflight/report.md`): the box has a second GPU (3080 Ti, the
   display); the 3090 is headless; its counter instance is `luid_..114dd`, not the brief's guess; the
   loaded-engine Shared Usage floor is 84-92 MiB, not ~86 MiB idle; `docker compose up` must run from
   PowerShell on this box — from Git Bash it rejects the `G:/models` bind mount.

## What could not be established

- E1-B2 at N≥8: the pool pre-empts above 5 resident requests, so those rows are tail measurements whose
  A-to-A spread (up to 13%) exceeds the B2 delta.
- Any C8 comparison: the cohort C8 protocol spreads 37% within one boot (248.8 vs 340.9, E1-A).
- E4: whether `low` answers as well as xhigh (no quality smoke was run; the arm touches no kernel).
- E2: whether B's GSM8K smoke (0.960 vs 0.980) is a real quality difference — that is one question at n=50.
- E6: whether 8192 changed checkpoint cadence at all (no log line), and cold-vs-cached follow-up TTFT (the
  probe kept only the best rep). The arm needs a checkpoint counter to answer on this pin.
- E5: strict A-B-A confirmation of the +3.3-4.1% (both A boots ran before B/C).
- E7: not runnable here (see table).

## Seen that the list did not ask for

- **FlashInfer boots hold Shared Usage at 220 (fp8) and 172 MiB (bf16) from the first request onward**, vs
  92 MiB on the other backends. Cutting the pool by 1 GiB (2.7 GB free VRAM) did not move it, and C1 moved
  only +4%, so it is a fixed host-side mapping of the FlashInfer path, not a working-set spill. The brief's
  rule would void those two arms on the counter alone; the reports record them as fail-by-downgrade with
  this caveat.
- **Free VRAM shrinks during runs**: 1.4-1.5 GB after boot, down to 423-921 MiB under load (allocator
  growth), with Shared Usage flat. The 1.3 GB rule is satisfied at boot but not continuously.
- The ladder's `run` column says the shipped profile is a ~5-resident-request server, not an 8-seat one:
  preemptions begin at N=8.
- `vllm serve --help=all` on this pin lists several unadvertised mamba knobs
  (`--mamba-backend`, `--enable-mamba-cache-stochastic-rounding`, `--mamba-ssu-algorithm`); recorded in
  `2026-10-13-image/raw-engine-probe.log`.
