1One door into the patch series

Strong

patches/seriesDockerfile:30-38verify.sh:52-86patches/check_vllm_series.shdocs/install.md:100-113docs/python-314.md:62-71kvarn/install.shpatches/dflash2-backport.patchREADME.md:119

Problem

The ordered patch series — the thing this repo is — has its apply logic re-encoded in five places: three near-identical sed parsers (Dockerfile, verify.sh, check_vllm_series.sh) and two prose copies in the docs. The prose copies have already drifted: install.md drops --fuzz 0 (so a moved hunk lands by guess instead of failing by name — the exact failure the fuzz-0 rule was created to prevent), and python-314.md still pins vLLM 0.27.1 with no skip logic. Meanwhile the retired dflash2-backport.patch is kept in the tree and special-cased in five consumers, the old 0.27.1 KVarN patches ride along as inert weight, and the README's front door still says "38 files" — there are 45. The fast CI gate never sees the two KVarN patches at all; only the 20-minute image build does.

Solution

One executable entry point — patches/apply.sh (parse series → apply --fuzz 0 → apply the KVarN pair) — that the Dockerfile, verify.sh, the CI checker and the docs all call, instead of each re-deriving it. Delete the retired artifacts (dflash2-backport, the 0.27.1 KVarN pair) so zero per-patch exceptions remain; their one-line obituaries already belong to PATCHES.md's "Retired" section, which is the project's own precedent (PATCHES.md:70-72). Folding the KVarN pair into the series check puts them under the 2-minute CI gate.

Benefits

  • Locality: apply policy lives in one file beside the series; a hunk failure names one script, not five suspects.
  • Leverage: the next pin flip (0.29 → 0.30) or new patch touches the series and its index — not five parsers and two docs. This is the change the repo makes most often.
  • Tests: one script is directly exercisable in CI against a pristine wheel; deleting special cases deletes untested branches rather than adding tests for them.

2Extract the shared launcher chassis

Strong

single-user/start_qwen.sh (822 lines)batch/start_qwen.sh (271 lines)resolve_config.shresolve_api_key.shsingle-user/select_model.sh

Problem

The two launchers are one file pasted twice, then drifted. 180 lines are byte-identical — 73% of batch's substantive code appears verbatim in single: the env prelude, the CUDA_HOME/nvcc-13 fix, the stale /dev/shm offload sweep, the TOOLS/METRICS/VISION blocks, the WSL2 + tensor-parallel allocator logic, key resolution, and 13 of ~18 exec-line flags. The drift is not hypothetical: the INT8 export guards already differ between the copies, batch carries a spec-decode metrics block that mode cannot produce, and single's VISION comment cites SPEC=dflash2 OOM measurements batch never runs. Every hard-won gotcha (#33 ghosts, #163 TP all-reduce, the nvcc fix in #185) has to be fixed in two files — and gotchas are this repo's lifeblood. resolve_config.sh was itself built as the F13 fix for exactly this class of bug.

Solution

A sourced launcher-chassis.sh that both modes source: the env/platform prelude, the allocator/TP decision tree, the TOOLS/METRICS/VISION flag builders, and key resolution. Each launcher keeps only what is genuinely mode-shaped — the CTX×SPEC profile branches in single, the KV profile branch in batch, and the final exec vllm serve line. Add a PRINT_ARGV=1 dry-run exit (print the assembled argv + resolved env, skip the platform-mutating exports, never exec) as the test seam.

Benefits

  • Locality: each gotcha lives once, next to its comment explaining which issue number it came from — today the comment and the fix can be edited apart.
  • Leverage: a new platform workaround (#185-style) is one edit that both modes inherit; resolve_config.sh's validation can then derive from the chassis instead of mirroring it.
  • Tests: PRINT_ARGV=1 turns ~40 gotcha conditionals into CI-assertable argv (CTX=huge ⇒ kvarn flags; TP>1 ⇒ expandable_segments:False) — no GPU needed. Zero shell tests exist today.

3One client module for the harness

Strong

Problem

"How to talk to our server" is ~1,500 lines of copy-paste across the harness, and the copies have already drifted in ways that produce real misfires. The API-key chain is implemented four different ways: the canonical one (resolve_api_key.sh: OPENAI_API_KEY → VLLM_API_KEY → api_key.txt → empty), a Python flavor in ~10 scripts that skips OPENAI_API_KEY, a second Python flavor that reads ~/qwen-serving/api_key.txt (a path nothing else uses), and one-off variants. Issue #113 fixed the bash scrapers to resolve the key properly; the Python scripts never got the memo — so a keyed server still reads as "spec-decode absent" to half the harness. Streaming, TTFT timing, metrics scraping and usage-field handling are likewise re-implemented per script with subtly different bugs.

Solution

A single bench/harness.py (or bench/lib/): client_key() implementing the canonical chain exactly, base_url(), model() (env override, else GET /v1/models — the server is the source of truth), post(), stream_chat() returning (ttft, chunks, usage), and metrics(*names). Scripts keep their workload logic — the part that is actually theirs. This passes the deletion test cleanly: deleting the module would re-concentrate the glue into 20 callers, which is precisely today's failure mode.

Benefits

  • Locality: the next auth/probe fix (#113's successor) lands once, not across four flavors discovered by grep.
  • Leverage: new reproducers and issue-oracles (this repo's main debugging instrument) halve in size; a script's diff shows its question, not its plumbing.
  • Tests: the glue is the CPU-testable part — key precedence, header injection, usage parsing can be unit-tested with a stub server, which is exactly where the field bugs have been.

4Deepen the preparation pipeline's shared core

Worth exploring

prepare/quant_lm_head.pyprepare/quant_embed.pyprepare/quant_mtp.pyprepare/quant_heads_stream.pydrafter/gptq_utils.pydrafter/export_mtp.pydrafter/requant_mtp_gptq.pydocker/prepare.sh:26-50

Problem

The model-preparation pipeline's two non-trivial operations — RTN quant math and the compressed-tensors write tail (weight_packed / weight_scale / weight_shape + weight_map edit + config-group clone + ignore-list edit + backup) — are re-implemented 8 times across prepare/ and drafter/. The differences that actually matter (fp16 vs bf16 scales) are invisible without diffing all eight. The MTP_LINEARS tensor list is defined in 6 files across 2 directories. A shared rtn_quantize exists in drafter/gptq_utils.py but prepare/ can't see it — and the drafter scripts reach it through a sys.path.insert shim duplicated 5×. The pipeline's tensor-name conventions are likewise known to docker/prepare.sh's embedded-Python state(), verify.sh, and the scripts themselves — three authors for one protocol.

Solution

A small shared module importable from both directories (no framework — a bag of functions): the quant math, the write tail with its variants expressed as data (scale dtype, group ordinal), the MTP_LINEARS constants, and one "assemble a variant dir" helper (hardlink/copy + fresh-write, encoding the inode-truncation guardrail that today travels by comment). The two loaders (in-RAM vs streaming) stay separate — both are load-bearing; only their shared internals move. Tensor names live next to their writers, and prepare.sh's state() predicates and the scripts read them from the same place.

Benefits

  • Locality: renaming a tensor or fixing the write tail edits one file; today the same edit must be replicated 6–8 times and verified by eye.
  • Leverage: the next quantization variant (the pipeline's whole reason to grow) becomes "call the core with different data," not "copy the nearest script and hope."
  • Tests: the math and the write tail are pure CPU tensor code — property-testable (round-trip, zero-point, ignore-list invariants) without a GPU, which none of the 8 copies currently has.

5Give the harness a verdict convention, and wire the CPU tests into CI

Worth exploring

bench/test_spec_decode_attn.pybench/api_smoke.pybench/mq3d_capacity_property.pybench/verbatim.pybench/test_model_verification.pybench/prefix_alternation.py.github/workflows/patch-integrity.yml

Problem

Of the ~37 files in the harness, exactly one gates CI (test_model_verification.py — and it reaches into verify.sh by string-splitting on a literal heredoc marker, so a reformat breaks CI with an IndexError). The rest cannot be composed into a gate even by hand, because pass/fail semantics are per-script and often absent: test_spec_decode_attn.py prints FAIL on a correctness miss and exits 0 anyway; api_smoke.py prints SUMMARY and exits 0 at 0/12; prefix_alternation.py returns 0 on the arm that reproduces the defect; exit 2 means "refusing to pass" in one script and "invalid tier" in another. Meanwhile two genuinely CI-able tests already exist and gate nothing: mq3d_capacity_property.py (pure stdlib, seconds, with a negative control) and verbatim.py's self-test.

Solution

Two cheap moves. (a) One verdict convention across the harness: exit 1 = the check ran and failed, exit 2 = the run itself was invalid, anything informational stays on stdout; scripts that only measure say so in their docstring and keep exiting 0. (b) Wire what is already CPU-safe into the workflows: mq3d_capacity_property.py (+ its --mutate negative control) and verbatim.py into patch-integrity.yml (seconds), mq3d_scratch_pool_test.py into the image build ("no GPU" per its own docstring). A short manifest table (script · kind · needs GPU/server/data · exit semantics) stops every reader re-deriving the taxonomy from 37 docstrings.

Benefits

  • Locality: a script's contract lives in its exit code and one table row, not in gotchas.md folklore (~20 scattered references today).
  • Leverage: reproducers become composable — a regression suite can be assembled from existing scripts instead of written anew per issue.
  • Tests: two real tests start gating for free; the heredoc string-split dependency in the one CI test is the natural next hardening (candidate 1 helps here too).

7Let each preparation step report its own done-ness

Worth exploring

docker/prepare.sh:26-50, 101the six prepare/ scriptsverify.sh:197-225bench/test_model_verification.py:15

Problem

"Is step X done?" for the model-preparation pipeline is authored three times: the scripts themselves (which know the real tensor names), docker/prepare.sh's state() — a Python heredoc living inside shell, pattern-matching weight_packed names out of the index — and verify.sh's model checks. The one CI test that exercises this (test_model_verification.py) does so by string-splitting the heredoc out of shell source on a literal marker. So the done-ness protocol of a ~20 GB artifact pipeline is maintained in a language the writers don't run, and tested through a parser of a parser. Rename a tensor and you edit the script, the heredoc, and verify.sh — miss one and prepare silently re-runs or skips a step.

Solution

Each prepare script grows a --status probe (script.py DIR --status → exit 0/1 + a one-line reason). The tensor names stay in the file that writes them; prepare.sh's state() becomes a loop over the probes and keeps only orchestration (flock, dispatch, the harden/translate passes). Keep verify.sh's checks as a deliberately independent second implementation — its skepticism (packed-geometry and zero-point cross-checks) is a feature; share names and predicates, not the verification semantics.

Benefits

  • Locality: the done-predicate for a step lives next to the code that performs the step — the heredoc stops being a third author.
  • Leverage: adding a pipeline step (third-party checkpoints are on the roadmap) is "write script with --status," not a three-layer edit across shell, Python and CI.
  • Tests: probes are cheap subprocess calls against tmp-dir fixtures in the existing test style — no shell-surgery parsing in CI.

Considered and set aside

The deletion test, applied honestly — these looked tempting and fail it:

  • Merging the two chat-template scripts (harden/translate) — concentrates nothing; each owns a distinct, well-commented transform.
  • Deleting _check_applied.py or export-patch.sh — both fail the shallowness test: they encode battle-scarred logic (content-tolerance heuristics, hunk-header surgery) that would just move into callers.
  • Merging check_vllm_series.sh's GNU-patch/git-apply passes — the split is load-bearing and documented in the file.
  • Merging the two launchers into one MODE-parameterized file — a possible endpoint of candidate 2, not a separate project; the chassis extraction already kills the duplication, and a merge mainly re-risks a 700-line file.
  • Splitting train_mtp.py — a research script with two consumers; no leverage.
  • A prepared_state.json manifest for the pipeline — versions a new format forever for a pipeline that runs once per model; candidate 7's probes get the same benefit without the format.

Top recommendation

Start with candidate 1 — one door into the patch series.

Three reasons. It is where the change pressure is: patches/ took 61 file-touches in the last 40 upstream commits — more than the next three areas combined — and the README says the quiet part out loud: "what this repo really is … is a patch series against a pinned vLLM." Deepening the module you change most pays the most.

The drift is not hypothetical: both prose copies of the apply loop have already diverged from the real one (one drops the fuzz-0 guarantee the series was rebuilt to enforce; the other still pins 0.27.1), and the front-door README undercounts the series by seven patches. Every month this waits, the five parsers get another chance to disagree — and the next pin flip (0.29 → 0.30, already foreshadowed by the three fork branch lines) is exactly the change this candidate makes easy.

It unlocks the others: with one apply door, the CI gate (candidate 5) can exercise the whole series — KVarN included — on a pristine wheel in two minutes instead of twenty, and the generated index (candidate 6) hangs off the same door. And the deletion half of the candidate (retired patches, inert 0.27.1 KVarN files, five copies of one special case) follows the repo's own remove-on-retire precedent — it is subtraction, not new machinery.

Sequence after that: 2 and 3 are independent and can run in either order; 5 is the cheapest card in the deck; 6 and 7 land best on top of 1.
