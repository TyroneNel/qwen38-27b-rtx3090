# GPU agent brief — decode-speed experiments on the RTX 3090 box

Paste the whole of this file as the task for the agent running on the Windows machine. It is written to be
executed literally; where it says "verify", the answer belongs in the report, not in your memory.

## Role

You are the operator of one Windows workstation with a single RTX 3090 (24 GB, power-limited to 250 W), Docker
Desktop with the WSL2 backend, and PowerShell. Your job is to run the experiments in
`docs/decode-speed-experiments.md` against the repo checked out at `G:/dev/HyperQwen`, commit the raw results
and reports to the branch `cline/gf59cdmh`, and push. Nothing else.

## The hard rules

1. **Speed is everything.** No soak tests, no `verify.sh` full runs, no acceptance batteries. One quality
   smoke on any arm that touches a kernel, dtype or backend, and no more.
2. **No assumptions.** Every fact in your report must be the output of a command you ran, quoted verbatim. If
   you did not verify something, write "not verified" — do not infer it, do not carry it over from this
   document, and do not fill a gap with what the docs say it should be.
3. **No pull requests, no issues, no comments, no reviews.** Never run `gh pr`, `gh issue`, `gh api` write
   calls, or anything that posts to GitHub. You commit and you push, to one branch.
4. **No co-authored commits and no watermarks.** Commit with the repo's configured identity, one author. No
   `Co-Authored-By:`, no `Signed-off-by:`, no "generated by", no tool or agent name, no badges, no emoji
   headers, no banners in any file you write. Your output should read like a human operator's lab notes.
5. **Only this branch.** `cline/gf59cdmh` on `origin`. Never commit to `main`. Never push to the `upstream`
   remote (`syv-ai/HyperQwen`) — its push URL is deliberately disabled; leave it that way.
6. **Do not fix the product.** The only file you may change outside `bench/results/` and `docs/` is the
   launcher knob permitted by E1, off by default, with its diff in the report. If an arm needs an engine
   patch, the arm's result is "needs an engine change" — not a patch.
7. **Leave the machine as you found it.** Containers down, no stray `docker run`, no new global config, no
   files outside the repo.

## Step 0 — preflight, before any build or boot

Run these and paste the output into `bench/results/<date>-preflight/preflight.txt`:

```powershell
cd G:\dev\HyperQwen
git status --short; git log --oneline -1; git rev-parse --abbrev-ref HEAD
git config core.autocrlf                 # must be false; this repo is LF-only (see .gitattributes)
nvidia-smi --query-gpu=name,memory.total,driver_version,power.limit,power.draw --format=csv
docker version --format '{{.Server.Version}}'; docker info --format '{{.OSType}}'
docker run --rm --gpus all nvidia/cuda:12.8.0-base-ubuntu24.04 nvidia-smi -L
Get-ChildItem G:\models | Select-Object Name
# idle baseline for the spill counter: run this for ~60s and keep the mean
Get-Counter '\GPU Adapter Memory(*)\Dedicated Usage','\GPU Adapter Memory(*)\Shared Usage' -SampleInterval 10 -MaxSamples 6
# the card as the engine will see it (free/total), before anything is loaded
nvidia-smi --query-gpu=memory.total,memory.used,memory.free --format=csv
```

Then answer, in the report, with evidence:

- Is the branch clean and at the expected commit? If the working tree is dirty, **stop** and report the diff
  rather than committing over it.
- Is `core.autocrlf` false? If not, set it false locally, re-checkout, and note it — a CRLF working tree
  breaks every bash script in the image.
- Is the GPU visible inside a container, and is the power limit actually 250 W? If it is not 250 W, say so in
  the first line of every report and mark all cross-references to published 250 W rows invalid. Do not try to

- What is actually in `G:/models`? List the directories. The launcher expects the prepared W4A16 target and a
  DFlash2 drafter under the names the repo uses (`single-user/select_model.sh` and the `SPEC=dflash2` branch of
  `single-user/start_qwen.sh` show the exact names it looks for). Do not guess names: read those two scripts,
  then compare with the listing.
- Free space on the drive Docker uses. The image is ~9.5 GB and the models are already on disk.
- Is a display attached to this card? If yes, say so: `KV_MEM` assumes a headless card and the pool must
  be dropped by whatever the desktop holds (gotcha 31, `docs/gotchas.md`).
- What is the idle Shared Usage baseline (expect ~86 MiB), and does it stay there? That number is the

## Step 2 — first boot

```powershell
cd G:\dev\HyperQwen
# .env is gitignored; it is the knob surface for every arm
"MODELS_DIR=G:/models" | Set-Content .env
"VLLM_WSL2_ENABLE_PIN_MEMORY=1" | Add-Content .env   # required on Docker Desktop/WSL2, or the V2 runner aborts with a UVA error

docker compose exec single bash -lc 'curl -sf -o /dev/null -w "%{http_code}\n" http://127.0.0.1:18020/health'
```

- Do not run the `prepare` profile unless Step 0 showed the model directories are genuinely absent. If they
  are absent, stop and report — do not download 20 GB on your own initiative.
- If the boot fails, read the error before doing anything: `docs/gotchas.md` is 1400 lines of exactly these
  failures, and `docs/docker.md` plus `docs/wsl2-4090.md` are the WSL2-specific ones. Grep them
  (`Select-String`) for the error text, and report which gotcha it matched.
- Once healthy, discard the first bench run (JIT warmup reads 30-50% low), then take the baseline.

## Step 3 — run the arms

Work through `docs/decode-speed-experiments.md` in order: E1, E2, E3, E4, E5, E6, then E7 only if time remains.
For each arm:

1. Write the arm's knobs into `.env` (that file is the only knob surface; do not pass env vars by hand on the
   command line, or the arm stops being reproducible from the committed files).
2. `docker compose --profile single up -d --force-recreate`, wait for health, then confirm from the **boot log**
   that the settings you asked for are the settings the engine got. Every arm's report starts with that
   confirmation. If the engine ignored a knob, the arm's result is "knob not applied" — that is a finding, not
   a failure.
3. Before measuring: read the engine's free-VRAM-after-boot figure out of the boot log and start the
   counter sampler from Step 4. **If free VRAM is under 1.3 GB, or Shared Usage climbs above the idle
   baseline, do not measure** — cut `KV_MEM` (or `MAX_LEN`) until both are clean, and record what you
   changed. A spilled run's tok/s is void; its tokens-per-step column is not.
4. Discard the first measurement after the boot. Keep the second.
5. Stop the server (`docker compose --profile single down`) before the next arm, so arms never share a boot.

Time-box: if an arm has not produced a number after twice its budget in the experiments doc, record what you
have, mark it "incomplete — time-boxed", and move on.

## Step 4 — memory headroom: the check that decides whether a number is real

Under WSL2/Docker Desktop the usable dedicated VRAM is ~0.5 GB below bare metal, and crossing that line does
not fail — it silently moves the overflow to host memory and the step runs **2-6× slower**. `nvidia-smi` shows
the card full either way. The repo's gotcha 53 (`docs/gotchas.md`) has the measurements; the rules for you:

1. **Leave ≥1.3 GB of free VRAM after boot** (the engine's own free figure). `docs/spec-decode-scratch-token-units.md`
   calls 319 MiB the "burst zone" and 1,323 MiB out of it.
2. **Sample the Windows counters for the whole run**, in a second PowerShell window:
   ```powershell
   Get-Counter '\GPU Adapter Memory(*)\Dedicated Usage','\GPU Adapter Memory(*)\Shared Usage' -SampleInterval 10
   ```
   Shared Usage at its idle baseline (~86 MiB) through the run means the working set is on the card. Anything
   above baseline means part of it is not. Save the trace beside the raw logs.
3. **Pin the pool by bytes, not by utilization**: set `KV_MEM` explicitly (and `MAX_LEN`) and keep them
   identical across the arms you compare. `GPU_UTIL` moves the pool with compile-cache state and with the KV
   dtype, which is exactly what E2 varies. Gotcha 31: `KV_MEM` assumes a headless card — if this box has a
   display attached, drop `KV_MEM` by what the desktop is holding, checked with `nvidia-smi` before the boot.
4. **If a spill is detected**, the arm's tok/s is void (its tokens-per-step column still stands — a spill moves
   memory, not arithmetic). Re-run with `KV_MEM` and/or `MAX_LEN` reduced until Shared Usage stays at baseline,
   and say in the report that the first attempt spilled and what you changed.
5. **KVarN (`CTX=huge`) spills at boot**, when its KV cache is allocated, before any request — check at startup,
   not during the run.
6. **Record the boot class.** Container vs native venv differ by ~500 MiB of residency on this repo's own
   measurements, so a row from this machine is only comparable to another container row.

## Step 5 — record and push

One directory per arm under `bench/results/<YYYY-MM-DD>-<arm-id>/`:

```
.env                     # the exact knob file used, KV_MEM and MAX_LEN included
cmd.txt                  # the exact commands, in order
image.txt                # image tag + digest, commit SHA, boot class
mem.txt                  # free VRAM after boot + the Shared Usage trace
raw-*.log                # verbatim stdout/stderr of every measurement, unedited
report.md                # the arm's table + verdict
```

`report.md` per arm: the arms side by side, the metric named, the raw numbers, the delta in percent, the
verdict (pass / fail / inconclusive — noise / knob not applied / spilled / incomplete), free VRAM after boot,
and one line on what was verified versus assumed. A delta under 3% is "no difference"; 3-10% needs A-B-A
before it is called; above 10% one boot per arm is enough. Then a top-level
`bench/results/<date>-SUMMARY.md`, one row per arm, with the single most useful number from each.

Commit and push:

```powershell
git add bench/results docs
git commit -m "exp: 3090 decode-speed arms E1-E5 (250W, <date>)"   # plain message, single author, no trailers
git push origin cline/gf59cdmh
```

Push after **each arm**, not at the end: the machine can be taken away at any time, and an unpushed result did
not happen. Never force-push, never amend a pushed commit, never rewrite history.

## Step 6 — report back

In your final message, and as the first section of the SUMMARY file: a table of arm, A, B, delta, verdict, and
the observed noise floor; then, in plain sentences, (a) what is now known that was not before, (b) what could
not be established and why, (c) anything you saw that the experiment list did not ask for but a human should
know — a crash, a silent config downgrade, a spill, a number that contradicts the docs. If an arm contradicted
`docs/decode-speed-landscape.md`, say so explicitly with the number; that page is a set of leads and is
expected to be partly wrong.

## Failure playbook

| symptom | do this |
|---|---|
| `RuntimeError: UVA is not available` | `VLLM_WSL2_ENABLE_PIN_MEMORY=1` is missing from `.env` (`docs/docker.md`) |
| decode suddenly 2-6× slower, no error | shared-memory spill. Check the Shared Usage counter, cut `KV_MEM`/`MAX_LEN`, re-run (Step 4) |
| bash errors mentioning `\r` or `$'\r'` | CRLF working tree: `git config core.autocrlf false`, re-checkout, rebuild |
| OOM at boot | record the engine's memory line, then raise `GPU_UTIL` headroom per `docs/gotchas.md`; if the arm caused it, that is the result |
| port 18020 already in use | `docker compose down`, check `docker ps`; do not change `PORT` mid-experiment |
| no GPU in the container | `docker run --rm --gpus all ... nvidia-smi -L`; if that fails, stop — nothing here can run |
| a model directory is missing | stop and report the listing; do not download |
| a knob is rejected by the engine | record the exact error, mark the arm "knob not applied", continue |
| boot fails and you do not recognize the error | grep `docs/gotchas.md` (`Select-String`) for the error text, report which gotcha it matched |
